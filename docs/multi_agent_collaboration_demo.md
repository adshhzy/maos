# 多智能体协作对比演示

本演示用于展示：同一个复杂任务，经过任务图拆分给多个专业智能体协作后，通常比单个通用智能体一次性完成更容易得到覆盖面完整、风险更清晰、执行计划更可靠的结果。

## 示例文件

多智能体协作图：

```text
examples/multi_agent_collaboration_ai_sales_pilot.json
```

单智能体基线图：

```text
examples/single_agent_baseline_ai_sales_pilot.json
```

两个图使用相同任务背景：为一家企业软件服务公司设计面向中型制造业客户的人工智能销售助手试点落地方案。

## 运行方式

1. 打开 Web UI。
2. 先加载并运行 `multi_agent_collaboration_ai_sales_pilot.json`。
3. 再加载并运行 `single_agent_baseline_ai_sales_pilot.json`。
4. 分别查看最终节点输出：
   - 多智能体图：`executive_synthesis`
   - 单智能体图：`single_generalist_solution`
5. 对比时不要只看篇幅，重点检查多智能体最终输出是否保留了专家节点来源、冲突取舍矩阵和专家结论附录。

## 多智能体图的角色分工

- `market_research`：市场与客户研究智能体
- `product_strategy`：产品与场景策略智能体
- `technical_architecture`：技术架构智能体
- `security_review`：安全与合规智能体
- `roi_model`：投入产出与商业价值智能体
- `delivery_plan`：上线交付与质量智能体
- `executive_synthesis`：总协调与完整交付包智能体

这些节点不是简单串行写作，而是形成了带依赖关系的协作图：

- 市场研究先给产品策略提供客户与采购背景。
- 产品策略约束技术架构的最小可行版本边界。
- 安全智能体同时审查市场、产品和架构方案。
- 投入产出智能体基于市场假设和产品范围计算试点价值。
- 交付智能体把技术、安全和投入产出约束转成 8 周执行计划。
- 总协调智能体综合所有专家输出，形成可提交评审的完整交付包，并保留专家证据链。

## 对比维度

建议从以下维度对比两个最终输出：

| 维度 | 多智能体输出应体现的优势 | 单智能体常见短板 |
| --- | --- | --- |
| 覆盖面 | 市场、产品、技术、安全、投入产出、交付均有专门视角，并在最终交付包中保留证据 | 容易覆盖宽但每块较浅 |
| 专业深度 | 每个专业节点能展开本领域约束和判断 | 容易给出通用建议 |
| 依赖关系 | 能看到上游结论如何影响下游方案 | 依赖链条不明显 |
| 风险处理 | 安全、合规、预算、交付风险被独立审查 | 风险项容易混在总述里 |
| 冲突折中 | 总协调节点必须输出跨职能冲突与取舍矩阵 | 容易缺少多视角博弈 |
| 可执行性 | 交付节点给出周粒度计划、验收和回滚 | 时间表和责任分工可能较泛 |
| 可追溯性 | 最终交付包标注来源节点，并附专家节点关键结论 | 只能看到一个最终输出，且不能证明经过专家复核 |

## 推荐展示话术

可以这样展示结果：

1. 单智能体可以较快给出完整方案，但它是一次性推理，专业视角之间没有显式分工和互相约束。
2. 多智能体图把同一任务拆成多个专家节点，每个节点只处理自己擅长的部分。
3. 下游节点通过节点间结构化传递接收上游结果，因此技术、安全、投入产出和交付计划都不是凭空生成，而是基于前面专家输出继续深化。
4. 最终 `executive_synthesis` 不只是汇总，而是生成完整交付包：高管摘要、市场、产品、技术、安全、投入产出、交付、风险回滚、冲突取舍和专家结论附录都要保留。
5. 单智能体基线应被视为“未审查草案”：它可以写得完整，但无法证明经过独立专家复核，也无法提供来源节点证据链。
6. 因此，多智能体的优势不只是“输出更长”，而是中间过程可审计、专业判断可追溯、跨职能约束更完整。

## 注意事项

- 两个示例都使用 Hermes provider。
- 为避免因为真实智能体输出不是严格 JSON 而中断演示，示例要求输出结构化 Markdown。
- 如果真实智能体运行时间较长，可以先运行单智能体基线，再运行多智能体图观察并行节点如何逐步完成。
